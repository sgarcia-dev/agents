# Hosted and remote browsers

Use a hosted browser only when the task needs off-machine execution, local resource overflow, or an owner-chosen remote identity. It is a different browser and login store from local Chrome. Review provider data handling, spend/session limits, location, site restrictions, and human login viewer before creating sessions. A cloud browser does **not** wake a sleeping local agent gateway.

Browser Use Cloud named sessions, hosted browser contexts/profiles, and a self-hosted Camofox service have different persistence and concurrency semantics. A session name identifies a controller/browser run, not a saved login. Require an explicit profile binding at creation when authenticated reuse is intended; confirm the provider actually applies it. Hermes's tested named cloud sessions did not automatically bind a saved profile. A direct profile-bound helper had site-specific restart results; do not present that as native Hermes support or universal persistence. Camofox's shared process can host separate users, but one crash can affect them all, and a saved storage-state file did not prove ChatGPT remained signed in after restart. Read `~/agents/capabilities/browser-hosted.md` for route-specific onboarding.

Pilot on a public page first. For a private pilot, let the owner sign in through the exact visible session, perform any provider-specific save/checkpoint while it is active, stop the browser, create a **new** browser with the same explicitly selected profile, and verify an account-only control on each target site. Distinguish browser restart, Mac reboot, and sleep/wake. Track the provider browser ID, tab, profile ID, cost, and ownership; stop only sessions the job created and read back zero active sessions when done. If the provider cannot prove explicit identity binding, treat the route as public-only.
