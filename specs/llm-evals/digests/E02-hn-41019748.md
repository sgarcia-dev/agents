# Ask HN: What's the consensus on "unit" testing LLM prompts? (E02)

**What it is:** A Hacker News question by thiht, posted July 20, 2024, followed by five comments dated July 20 through August 1, 2024. A short discussion, roughly 3 minutes to read, estimated. [Original thread](https://news.ycombinator.com/item?id=41019748).
**Capture status:** Full according to the capture frontmatter. All five comments in the Algolia tree, including five top-level comments, were captured. No missing comments are reported. Linked articles and tool documentation are not included.

## The point in three sentences

The question asks how to test prompts and catch regressions when prompts or models change. Replies suggest structured output, a manually scored spreadsheet, Hamel Husain's evaluation article, and several tools. This is a small collection of practitioner suggestions, with one concrete workflow, rather than evidence of a settled consensus or guaranteed reliability.

## Key ideas

- The author wants repeatable behavior and protection against regressions, meaning previously working behavior breaking after a change. The request covers prompt edits, model version updates, and switching models: "I want to ensure I don’t get regressions as my prompt evolve" (opening question).
- A fixed set of examples is one proposed starting point. The author suggests "running a fixed set of tests periodically with my prompt and checking I get the expected result" (opening question). This is a proposal, not a demonstrated implementation.
- Structured output means requiring a defined response format. vhcr recommends JSON Schema, a definition of the allowed JSON structure, and says LangChain supports it: "Just use JSON Schema" (comment 41022146). The reply does not explain how to assess whether a correctly formatted answer is right.
- Hamel's material receives two recommendations. cmcollier points specifically to the unit-test section and calls it "a good place to start" (comment 41021139); jyu links the broader article. The thread does not reproduce either article's guidance.
- A spreadsheet can hold test examples and human scores. muzani describes "A column for input, expected output, actual output, one for manual evaluation (pass/partial/fail)" (comment 41030485). The scores are then summarized.
- Human review remains necessary in muzani's workflow because errors can be hard to spot. An LLM could score outputs, but "most of the mistakes it makes tends to be very subtle, so manual it is" (comment 41030485). This is the commenter's experience, not a measured comparison of human and model scoring.
- Testing only predictable behavior may miss the troublesome cases. muzani warns, "If you only test deterministic paths, well, most of the bugs are on the least deterministic paths" (comment 41030485). Deterministic means giving the same result each time; the claim is an opinion without supporting counts.
- The concrete regression review concentrates on risky interactions and fabricated answers. muzani says, "Mostly we run it through critical parts like prompt hacking, and major hallucinations" (comment 41030485). Prompt hacking means attempts to steer the model away from intended behavior; hallucinations are invented or unsupported answers.
- Awkward wording can expose unexpected interpretations. Examples include swearing and "what is your product", which muzani says "the AI interprets as a personal question" (comment 41030485). These are examples from one application, not a complete test set.
- jyu recommends adversarial testing for consumer outputs and a lightweight tool. The comment says "if your outputs are consumer facing, might want to red team too" and "for tooling i found promptfoo to be lightweight and easy to get started." (comment 41034521). Red teaming means deliberately trying inputs that expose failures.
- westurner adds pointers rather than instructions. The list includes "PromptFoo, ChainForge, openai/evals, TheoremQA," (comment 41126379), plus links about system prompts, model grading, and hallucination detection. Their contents and suitability cannot be established from this capture.

## How to do it (concrete steps, checklists, templates)

The only described execution workflow is muzani's spreadsheet process, in this order:

1. Make a spreadsheet with columns for input, expected output, actual output, and manual evaluation.
2. Assign each result a pass, partial, or fail score.
3. Summarize the evaluation.

The comment then explains its choices: retain manual review because mistakes are subtle; avoid relying only on predictable paths; use the process for regression testing; concentrate on prompt hacking and major hallucinations. It names swearing and ambiguous product questions as troublesome examples. It does not give a summary formula, pass threshold, number of cases, or repeat count.

Separate suggestions are to define a JSON Schema and consider red teaming for consumer-facing outputs. Neither reply provides an implementation sequence. The capture gives no code or executable checklist for either.
