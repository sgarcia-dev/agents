# Browser Use Decisions

## September 24, 2026: promote browser use as a cross-harness topic

Browser use will grow beyond one Jev package or one agent. Keep a portable [spec.md](./spec.md) for the behavior and safety contract. Tool-specific settings remain with their respective harnesses; no single session should silently reconcile several native configs. The Jev research record is evidence for the first implementation, not a universal browser policy.

## September 29, 2026: one shared skill with progressive references and a broader bridge registry

The owner chose one `/browser-use` skill that starts with recommendations and loads focused route references only when needed. Keep this spec authoritative for cross-harness behavior, the shared skill for route procedure, website skills for site-specific actions, capability guides for each connection standard, and harness wrappers for native calls. The connector registry must include non-MCP browser/desktop bridges; a giant MCP-only file would obscure native, CLI, API and desktop routes. Curated browser MCP entries remain configured default-off unless that harness has a dated enablement decision; optional awareness-only bridges are inventoried, not automatically installed. `/sync-tool-adapter` handles one harness per run and verifies its actual public/signed-in route rather than inferring access from documentation. Do not copy logins, tokens or profile data between harnesses, or claim equivalent capabilities merely because a skill synced. This supersedes the earlier assumption that browser-native bridges could not be candidates for shared documentation; their implementation remains harness-local.

## September 24, 2026: record the owner's authenticated-browser goal without claiming deployment

**Historical proposal, superseded by later tests below.** The owner's new handoff (private, not published) adds a requirement the anonymous Jev browser cannot meet: an inspectable, persistent, manually signed-in session reachable from a Mac-hosted agent when the owner sends a remote instruction. Prefer a dedicated visible Chrome user-data directory and loopback-only CDP as the first candidate over copying the ordinary Chrome profile. Chrome documents that newer releases ignore debugging flags against the default user-data directory; Hermes documents an existing `browser.cdp_url` route. The alternative Chrome `--autoConnect` flow asks the owner to approve a connection each session, which conflicts with unattended phone requests. This tradeoff was a proposal at the time; subsequent local tests are below.

Do **not** fold this route into the existing Jev MCP. Jev remains separate for bounded, mostly anonymous navigation. Authentication belongs to the browser identity, not the choice model. Do not treat a shared CDP port as tool-level isolation or connection convenience as permission to perform account actions. Preserve a manual login/MFA handoff and start with one low-stakes site.

The Playwright MCP server initially had a historical `trust: trusted` entry, but the live post-restart configuration uses `trust: full` for Playwright and Jev. An explicit request naming the browser job counts as approval for its requested scope; ask again only for a material site or intent expansion. Avoid per-click or redundant per-write prompts. Hermes shell approval is distinct. A hard per-job permission broker has not been implemented.

The extension's first successful tab listing required the owner to approve access in a Chrome tab opened by the extension. That **browser-local approval** is distinct from Hermes's one-job consent. This was the initial state; the later token-backed test below removed the repeated local connection prompt in the observed runs.

## September 24, 2026: permit bounded parallel reads with owned tabs

Three Hermes subagents completed simultaneous read-only checks across two signed-in Chrome identities: one extension-driven ChatGPT tab in `sergei-automation`, plus separate ChatGPT and Claude tabs controlled by independent CDP connections in `agent-chrome-data`. The successful execution windows overlapped for 7.284 seconds and account-only controls/routes and own URLs passed read-back. The two CDP workers used a shared deterministic script with different arguments, not independent free-form browser reasoning. A prior single-process three-CDP-tab check also passed, as did a signed-in Chrome plus two isolated logged-out Chrome processes. Both CDP subagents initially timed out waiting for a scheduled start and then retried successfully; this is a scheduling failure, not a browser task failure. Use a sufficient wait deadline or an explicit barrier rather than timing out before the start signal.

**Choice:** Do not serialize every harmless read-only job merely because it uses the same browser. Give each worker an owned tab or separate browser identity, recheck origin, account-only state and final URL, and keep outputs scoped to that job. Prefer the two existing signed-in identities when a task needs isolation of browser cookies and storage; do not create a third persistent profile for public work. Still serialize same-tab actions, account-changing operations on the same site, clipboard/download/native-dialog use, and any controller that cannot pin or verify its tab. Cross-profile storage separation is not an authorization boundary and cannot prevent two agents from changing the same remote account. Sustained multi-agent workflows and restart/sleep resilience remain unverified.


## September 24, 2026: close owned tabs, retain shared Chrome

The owner reports accumulating tabs and a heavy browser after repeated agent sessions. A current CDP inventory showed **17 page targets out of 30 total targets**; it does not identify which tabs are stale or agent-owned, so do not bulk-close them. Previous short CDP scripts called `page.close()` and disconnected; the recent extension worker navigated an existing connection without a recorded tab-close check. We cannot claim the existing backlog was cleaned or attribute all page targets to these tests.

**Decision:** A job must track and close every tab it creates, including the last owned tab, on success, failure, timeout and delegated completion. Verify disappearance; a worker's handoff must include cleanup status, and the parent must check it. If exact ownership is unknown or closing fails, report the debt and perform targeted recovery rather than risking the owner's or another worker's tab. Do not force-quit the persistent signed-in Chrome automatically. A last-tab heuristic is unsafe during concurrent jobs and owner handoff; it can kill the shared CDP listener and disrupt other sessions. An exclusive disposable browser process can be closed by its owning job after its tabs are closed. Any idle shutdown for shared Chrome needs a separate ownership/lease check and explicit decision. Closing tabs controls per-tab accumulation; it does not prove browser memory falls to zero or fix a site/process leak.

## September 24, 2026: certify exports by content, not by a button or turn count

The owner expects to request a complete Markdown copy of an individual ChatGPT or Claude conversation, including both parties and research reports. The September 24 pilots only proved bounded **rendered-content snapshots**, not that complete archive. Treat native per-message Copy, local per-thread export, Share, and account-wide export as distinct routes, and do not infer success from the presence of a control. Require every turn's ordered text and Markdown structure, top/bottom and hydration checks, citation/link targets, expanded research sections and attachments to be accounted for. Mark omissions in the deliverable. On this CDP/host setup the initial native Copy results were inconsistent or left the clipboard unchanged, and the inspected conversation menus had no local Save/Export/Download action. A later owner-targeted last-response experiment **did** repeatably copy one Markdown response through local Playwright and Hermes `browser_exec` when the target section was selected and a fresh clipboard marker was checked; an independent DOM conversion captured all visible word tokens, with minor differences from Copy. This narrows the failure to click targeting, clipboard read permission, or test setup rather than a universal site defect. The extension MCP's Copy click still failed through pointer interception, so do not claim that adapter passed. Avoid repeating the same clicks indefinitely; use target-bound controls, separate clipboard write from browser-side read, and choose a second extraction route when exact visible-text coverage matters.

Store private transcripts and raw clipboard evidence outside the coworker-visible workspace. **Practical route for ordinary ChatGPT conversations:** use the now-verified response Copy behavior as a per-turn building block, copy each user and assistant turn from its own section with a fresh marker, assemble in observed order, then verify the complete turn inventory. This is an accepted method to attempt, not a claim that a full thread has already passed the final completeness audit. Keep exact observed selectors in Hermes skills and the portable acceptance rule in the spec. The synthetic Claude two-file project test passed upload, retrieval and removal; ChatGPT's project-file persistence/retrieval did not. Neither mode switch alone proved local filesystem access.
